Teste como contrato

Testes que podem falhar de verdade

Não basta ter teste: ele precisa provar algo. No pipeline há testes que injetam o erro e exigem que a validação o detecte (fato sem linha, valor errado, grão duplicado), e testes de integração contra bancos reais, num schema isolado. Um deles força uma falha no meio de uma carga e confere que o banco ficou como estava. Cada bug que apareceu virou teste de regressão.

  1. Injeta o erro
  2. Exige a falha
  3. Confere o estado final

Evidência: tests/ do pipeline e test_dag.py. O projeto privado tem 50 arquivos de teste.

Decisão registrada

Escolhas com custo escrito, não só o resultado

Decisões que valem a pena lembrar viram um ADR. Um exemplo, no projeto privado: o estado do monitoramento só é confirmado depois que o aviso é enviado com sucesso. Assim, uma falha no envio não faz o evento se perder; o custo aceito é uma possível duplicidade, que é preferível à perda silenciosa. A decisão diz o que se ganha e o que se paga.

  1. Contexto
  2. Decisão
  3. Custo aceito

Evidência: projeto privado (docs/adr). Nos públicos, as seções "o que NÃO está resolvido" fazem o mesmo papel.

Honestidade técnica

Documento o que não foi verificado

Cada projeto tem uma seção com o que foi executado e o que não foi, e outra com as limitações. Quando uma revisão independente achou problemas (status nulo sumindo da fato, desconto fora da faixa, carga que não era atômica), eles foram corrigidos e ficaram registrados no README, junto com a hipótese que eu tive errada no caminho. Números de dados sintéticos vêm com o aviso de que não revelam padrão de negócio.

  1. Executa
  2. Registra o que passou
  3. Registra o que falta

Evidência: README do pipeline e README da orquestração.
