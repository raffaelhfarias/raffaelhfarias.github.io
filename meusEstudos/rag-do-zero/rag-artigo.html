Como construir um RAG do zero com Python

Como fazer um modelo encontrar o parágrafo certo de um manual interno antes de responder? Neste projeto, construímos esse fluxo com Python, embeddings, FAISS e um modelo de linguagem no Google Colab.

PythonEmbeddingsFAISSTransformersGoogle Colab

Por que criar um RAG?

Imagine perguntar quais são os dias de trabalho remoto de uma empresa cujo manual o modelo nunca viu. Um LLM sozinho pode responder com base em padrões aprendidos, mas não tem como consultar esse documento privado ou atualizado.

RAG, ou Retrieval-Augmented Generation, combina duas operações: primeiro recupera informação relevante de uma fonte externa; depois entrega essa informação ao modelo para gerar a resposta. Isso reduz a dependência da memória do modelo, mas não transforma a resposta em uma garantia automática de verdade.

Vamos acompanhar o mecanismo sem esconder as etapas atrás de um framework: texto, chunks, vetores, busca, contexto, modelo e resposta.

A pergunta central: antes de o LLM responder, qual trecho do documento ele recebeu?
Objetivo: entender o fluxo do RAG sem esconder as partes importantes atrás de um framework. A primeira versão não terá API, agentes, banco externo ou interface.

O que realmente acontece dentro de um RAG

RAG não é uma tecnologia única. É a combinação de uma etapa de preparação do conhecimento com uma etapa de consulta.

Como ler os outputs: use as saídas para conferir cada etapa. A quantidade de texto pode variar conforme o conteúdo do documento e as versões das bibliotecas.

  1. Documento
  2. Chunks
  3. Embeddings
  4. Índice FAISS
  5. Pergunta
  6. Resposta

Indexação

O documento é dividido em chunks, cada chunk vira um embedding e os vetores são adicionados ao FAISS. Esse fluxo prepara a base para consultas futuras.

Consulta

A pergunta também vira um embedding. O FAISS procura os vetores mais próximos, os chunks recuperados formam o contexto e só então o LLM recebe contexto mais pergunta.

INDEXAÇÃO:
Documento → Chunks → Embeddings → FAISS

CONSULTA:
Pergunta → Embedding → FAISS → Chunks relevantes
→ Contexto + Pergunta → LLM → Resposta

Passo 2

Carregar o documento

O documento é a base de conhecimento do sistema. Nesta primeira versão usamos apenas um arquivo de texto pequeno, para conseguirmos inspecionar o caminho completo da informação.

with open("knowledge.txt") as f:

O arquivo de exemplo contém políticas de trabalho remoto, férias, tecnologia e suporte. Faça perguntas apenas sobre esse conteúdo no primeiro teste.

Passo 3

Dividir o texto em chunks

O modelo não deve receber um documento inteiro de uma vez. O splitter limita o tamanho dos chunks e mantém uma pequena sobreposição para preservar o contexto entre cortes.

from langchain_text_splitters import RecursiveCharacterTextSplitter

with open("knowledge.txt") as f:
    knowledge_text = f.read()

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=250,
    chunk_overlap=30,
    separators=["\n\n", "\n", ". ", " ", ""],
)

chunks = text_splitter.split_text(knowledge_text)

print(f"We have {len(chunks)} chunks:")
for i, chunk in enumerate(chunks):
    print(f"--- Chunk {i+1} ---\n{chunk}\n")
Saída esperada
We have 3 chunks:
--- Chunk 1 ---
Manual interno da empresa

Trabalho remoto: os funcionários podem trabalhar remotamente às segundas e sextas-feiras. Às terças, quartas e quintas-feiras, o trabalho deve ser presencial.

--- Chunk 2 ---
Férias: funcionários em período integral recebem 20 dias de férias por ano. O saldo é acumulado mensalmente.

Tecnologia: o backend oficial utiliza Python. O frontend utiliza React. Aplicações móveis utilizam React Native.

--- Chunk 3 ---
Suporte: solicitações de suporte devem ser abertas no sistema interno durante o horário comercial, de segunda a sexta-feira, das 08h às 18h.

O ponto principal desta etapa é verificar os chunks antes de gerar embeddings. Se uma política estiver misturada com outra, a busca pode recuperar um contexto confuso. Chunking não é uma formalidade: ele influencia diretamente o que o modelo verá depois.

Passo 4

Criar embeddings

Um embedding transforma cada chunk em uma lista de números que representa seu significado semântico.

from sentence_transformers import SentenceTransformer

embedding_model = SentenceTransformer(
    "all-MiniLM-L6-v2"
)

chunk_embeddings = embedding_model.encode(chunks)

print(chunk_embeddings.shape)
Saída esperada
(3, 384)

O all-MiniLM-L6-v2 transforma cada chunk em um vetor com 384 posições. Essas posições não representam palavras legíveis nem entendimento humano; são uma representação numérica usada para comparar proximidade semântica.

Passo 5

Criar o índice FAISS

FAISS armazena os vetores e encontra rapidamente os mais semelhantes ao vetor de uma pergunta.

import faiss
import numpy as np

d = chunk_embeddings.shape[1]

index = faiss.IndexFlatL2(d)

index.add(
    np.array(chunk_embeddings).astype("float32")
)

print(f"FAISS index created with {index.ntotal} vectors.")
Saída esperada
FAISS index created with 3 vectors.

IndexFlatL2 faz uma busca exata pela distância entre vetores. Neste exemplo, o índice contém apenas três vetores, então essa solução simples é suficiente. Em produção, volume, latência e persistência podem exigir outras estratégias.

Passo 6

Carregar o modelo de linguagem

Até aqui preparamos e recuperamos informação, mas ainda não existe geração. Esta célula carrega o tokenizer e o modelo Qwen que serão usados para transformar contexto e pergunta em texto.

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

llm_name = "Qwen/Qwen2.5-1.5B-Instruct"

tokenizer = AutoTokenizer.from_pretrained(llm_name)

llm_model = AutoModelForCausalLM.from_pretrained(
    llm_name,
    torch_dtype="auto",
    device_map="auto"
)

Na primeira execução, o Colab baixa os arquivos do modelo. Essa etapa pode demorar porque o modelo é maior que o modelo de embeddings.

Passo 7

Criar generate_answer

Esta função recebe o contexto recuperado e a pergunta, monta as mensagens e chama o modelo para gerar uma resposta curta em português.

def generate_answer(context, query):
    messages = [
        {
            "role": "system",
            "content": (
                "Você responde perguntas usando somente o contexto fornecido. "
                "Se a resposta não estiver no contexto, diga que não há "
                "informação suficiente."
            )
        },
        {
            "role": "user",
            "content": f"""
Contexto:
{context}

Pergunta:
{query}

Responda em português, de forma curta e objetiva.
"""
        }
    ]

    text = tokenizer.apply_chat_template(
        messages,
        tokenize=False,
        add_generation_prompt=True
    )

    inputs = tokenizer(
        text,
        return_tensors="pt"
    ).to(llm_model.device)

    outputs = llm_model.generate(
        **inputs,
        max_new_tokens=80,
        do_sample=False
    )

    generated_tokens = outputs[0][inputs["input_ids"].shape[1]:]

    return tokenizer.decode(
        generated_tokens,
        skip_special_tokens=True
    )

A função não busca documentos. Ela representa a etapa de generation: recebe o contexto produzido pelo retrieval e o coloca junto da pergunta. Sem a recuperação anterior, o modelo não teria a evidência específica do manual.

Passo 8

Criar answer_question

Esta é a ligação entre retrieval e generation. Para cada nova pergunta, a função calcula um novo embedding, consulta o índice FAISS e monta um novo contexto antes de chamar generate_answer.

def answer_question(query):
    # RETRIEVE
    query_embedding = embedding_model.encode(
        [query]
    ).astype("float32")

    distances, indices = index.search(
        query_embedding,
        k=1
    )

    retrieved_chunks = [
        chunks[i]
        for i in indices[0]
    ]

    context = "\n\n".join(retrieved_chunks)

    # GENERATE
    answer = generate_answer(context, query)

    print("--- CONTEXT ---")
    print(context)
    print("-----------------")

    return answer
Importante: esta célula apenas define a função. Ao executá-la sozinha, nenhum texto será impresso. A função será executada quando você chamar answer_question(query_1) na próxima célula.

Quando a função é chamada, ela imprime o contexto recuperado antes de retornar a resposta gerada. O k=1 é uma simplificação didática: recuperamos apenas o chunk mais próximo para deixar a relação entre fonte e resposta fácil de observar.

Passo 10

Código completo usado no rag_colab.ipynb

Depois de entender cada bloco, leia o fluxo inteiro como uma sequência de células.

from langchain_text_splitters import RecursiveCharacterTextSplitter
from sentence_transformers import SentenceTransformer
import faiss
import numpy as np
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

with open("knowledge.txt") as f:
    knowledge_text = f.read()

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=250,
    chunk_overlap=30,
    separators=["\n\n", "\n", ". ", " ", ""],
)
chunks = text_splitter.split_text(knowledge_text)

print(f"We have {len(chunks)} chunks:")
for i, chunk in enumerate(chunks):
    print(f"--- Chunk {i+1} ---\n{chunk}\n")

embedding_model = SentenceTransformer("all-MiniLM-L6-v2")
chunk_embeddings = embedding_model.encode(chunks)

print(chunk_embeddings.shape)

index = faiss.IndexFlatL2(chunk_embeddings.shape[1])
index.add(np.array(chunk_embeddings).astype("float32"))

print(f"FAISS index created with {index.ntotal} vectors.")

llm_name = "Qwen/Qwen2.5-1.5B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(llm_name)
llm_model = AutoModelForCausalLM.from_pretrained(
    llm_name,
    torch_dtype="auto",
    device_map="auto",
)

def generate_answer(context, query):
    messages = [
        {"role": "system", "content": (
            "Você responde perguntas usando somente o contexto fornecido. "
            "Se a resposta não estiver no contexto, diga que não há "
            "informação suficiente."
        )},
        {"role": "user", "content": f"""
Contexto:
{context}

Pergunta:
{query}

Responda em português, de forma curta e objetiva.
"""},
    ]

    text = tokenizer.apply_chat_template(
        messages,
        tokenize=False,
        add_generation_prompt=True,
    )
    inputs = tokenizer(text, return_tensors="pt").to(llm_model.device)
    outputs = llm_model.generate(**inputs, max_new_tokens=80, do_sample=False)
    generated_tokens = outputs[0][inputs["input_ids"].shape[1]:]
    return tokenizer.decode(generated_tokens, skip_special_tokens=True)

def answer_question(query):
    # RETRIEVE
    query_embedding = embedding_model.encode(
        [query]
    ).astype("float32")

    distances, indices = index.search(
        query_embedding,
        k=1
    )

    retrieved_chunks = [
        chunks[i]
        for i in indices[0]
    ]

    context = "\n\n".join(retrieved_chunks)

    # GENERATE
    answer = generate_answer(
        context,
        query
    )

    print("--- CONTEXT ---")
    print(context)
    print("-----------------")

    return answer

query_1 = "Quais são os dias de trabalho remoto?"

print(f"Query: {query_1}")
print(f"Answer: {answer_question(query_1)}")

O que esta implementação ainda não resolve

Este projeto foi deliberadamente reduzido para que o mecanismo fique visível. Isso também define seus limites:

  • há uma única fonte de conhecimento e poucos chunks;
  • recuperamos apenas k=1, sem reranking;
  • não há metadados, avaliação formal ou persistência do índice;
  • o documento precisa ser pequeno e estar disponível no ambiente;
  • o modelo de geração é pequeno e pode cometer erros;
  • não há API, interface, autenticação ou monitoramento.

Além disso, recuperar um chunk relevante não garante que o LLM interpretará tudo corretamente. RAG reduz a dependência de conhecimento paramétrico, mas não elimina alucinações nem substitui avaliação.

Próximos experimentos

Depois de entender o fluxo atual, experimente uma variável por vez:

  1. altere chunk_size e chunk_overlap;
  2. recupere k > 1 e compare o contexto enviado ao modelo;
  3. normalize os embeddings e compare estratégias de similaridade;
  4. adicione múltiplos documentos e metadados;
  5. teste outro modelo de embedding e outro LLM;
  6. meça separadamente a qualidade da recuperação e da resposta;
  7. só depois considere persistência, API e interface.

Conclusão

Chegamos ao final da primeira versão do projeto. Agora já é possível acompanhar o caminho completo entre um documento, uma pergunta e a resposta produzida pelo modelo.

O RAG deixa de parecer uma caixa-preta quando separamos suas responsabilidades. O índice não responde; ele recupera. O LLM não consulta o documento sozinho; ele recebe o contexto que o pipeline selecionou.

Em essência, o fluxo é simples: encontrar o contexto certo antes de pedir ao modelo que responda.

Resumo: documento → chunks → embeddings → FAISS → contexto + pergunta → LLM → resposta.

Este projeto foi construído para tornar esse fluxo observável e servir como base para experimentos mais completos em AI Engineering.
